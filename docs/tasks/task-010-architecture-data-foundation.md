# Task 010 — Architecture / Data Foundation

## Status

**IMPLEMENTED**

## Scope

Established the database and access foundation for future transaction CRUD. No transaction CRUD, page integration, category persistence, dashboard data integration, or reports data integration was added.

## Data Model

The existing schema provides user-owned `transactions`, `categories`, and `payment_methods` tables. Each row is owned by `clerk_user_id`, which stores the Clerk JWT `sub` claim.

Transactions contain:

| Field               | Database type   | Contract                                        |
| ------------------- | --------------- | ----------------------------------------------- |
| `id`                | `uuid`          | Primary key, generated by `gen_random_uuid()`   |
| `clerk_user_id`     | `text`          | Required Clerk subject; enforced by RLS         |
| `amount`            | `numeric(12,2)` | Required and greater than zero                  |
| `type`              | `text`          | Required; `income` or `expense`                 |
| `description`       | `text`          | Required and non-blank                          |
| `category_id`       | `uuid`          | Required reference to an owned category         |
| `payment_method_id` | `uuid`          | Required reference to an owned payment method   |
| `date`              | `date`          | Expense/income date; defaults to `CURRENT_DATE` |
| `created_at`        | `timestamptz`   | Database creation time; defaults to `now()`     |

The `type` field aligns storage with the product specification's income/expense distinction. Category and payment method names remain normalized in their own tables and are not copied onto transaction records.

The frontend row contract is the database field names above, with UUIDs and text represented as JavaScript strings, `amount` represented as a number from PostgREST JSON, `type` constrained to the two string values, `date` represented as `YYYY-MM-DD`, and `created_at` represented as an ISO timestamp. A display view may include joined `{ id, name }` category and payment-method objects; these are query results, not duplicated transaction columns. Loading, error, and empty-list states belong to the future data-consuming page and are not implemented in this foundation task.

## Ownership and Data Flow

```text
Clerk session
    ↓ access token
Supabase client accessToken provider
    ↓ validated JWT
PostgreSQL RLS checks auth.jwt() ->> 'sub'
    ↓
Rows where clerk_user_id matches the Clerk subject
```

`createSupabaseClient(getAccessToken)` creates a Supabase client using the public Supabase URL/key and the provided Clerk token callback. The database remains responsible for ownership enforcement; client-provided ownership values are not trusted. No service-role key or server-only credential is used in browser code.

RLS remains enabled for all three user-owned tables with per-operation policies. Composite foreign keys bind each transaction's category and payment method to the same `clerk_user_id`; `ON DELETE RESTRICT` prevents deleting referenced rows. Existing user-scoped indexes and duplicate-name constraints are retained.
